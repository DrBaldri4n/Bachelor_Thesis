\subsection{Holistic Dataset Comparison}
So far, we have provided an overview of the relevance and challenges involved in securing EVSE environments. We discussed the fundamental knowledge required before developing an anomaly detection system, gained insight into related work in this area, and explored how it can inform our own approach.\\
We have also examined how data can be acquired from EVSE environments and how \texttt{Prometheus} can be used to collect and store this data.\\
All of these sections and subsections are essential for understanding the context of our work and for showing how it is possible to develop an anomaly detection system for EVSE environments based on the analysis of hardware events and the collected data.\\
In this section, we focus on the Exploratory Data Analysis (EDA) of the collected data. EDA is a crucial step in understanding the data, identifying patterns, and preparing for further analysis or modeling. We use Python and its data analysis libraries within a Jupyter Notebook environment to visualize and explore the collected data. The Python libraries utilized for data processing and visualization are explained in more detail in Chapter~2.2 (Fundamentals), providing a foundational understanding of the tools applied in this analysis. Establishing this methodological basis is crucial, as the quality of the results in the following chapters and significantly influences how well anomaly detection using machine learning models will perform and how quickly they will learn. Therefore, we need to answer the following questions:
\begin{itemize}
    \item Is there any noise in the data, and how significant is it?
    \item Can we observe meaningful distributions in the features over time and in relation to attacks?
    \item How strong are the correlations between the different features?
    \item Can we identify and define the most important features?
\end{itemize}
Answering these questions through Exploratory Data Analysis (EDA) provides a foundation for effective feature selection and model performance \cite{google2024EDAFeatureSelection} futhremore we will compare all results with the dataset CICEVSE2024 to garanty to have a meaningful result and can transfer the results to other charging station setups.\\
We start with analizing the framework conditions of both datasets, the public dataset CICEVSE2024 and the self-collected dataset.\\
% warum ist der Vergleich wichige? zwischen den beiden Datensätzen
The paper \textit{Enhancing EV Charging Station Security Using a Multi-dimensional Dataset}~\cite{EV_Security} and my work pursue the same goal: detecting anomalies through the analysis of HCP and kernel events. Therefore, it is essential to compare the underlying datasets on which the machine learning algorithms are trained. Such a comparison enables validation of the respective approaches and helps determine whether the results can be generalized.

We tried to get as close as possible to the environment of the paper \textit{Enhancing EV Charging Station Security Using a Multi-dimensional Dataset}\\

We also used a Raspberry Pi to represent the EVSE-B and employed a wattmeter to monitor power consumption. The combination of HCP events, kernel events, and power consumption measurements will be discussed in future work. As mentioned in Chapter~\texttt{Data Sources for EVSE Anomaly Detection}, we also used the \texttt{perf} tool to monitor the various events.\\
\\

Therefore, we are able to observe approximately 900 events in our dataset, which is comparable to the reference dataset. The complete observation period spans from \texttt{2025-07-22T18:00:00} to \texttt{2025-07-23T12:52:10}, with a sampling interval of 5 seconds, identical to the compared dataset \cite{EV_Security}. This results in approximately 8,000 data rows and 905 columns. Importantly, no missing (\texttt{NaN}) values are present, and all measurements were collected using the \texttt{perf} tool, producing logically consistent outputs as described in the chapter \textit{Data Sources for EVSE Anomaly Detection}.  

To ensure comparability, features distributed across multiple CPU cores (e.g., \texttt{cpu=0,1,2,3}) were aggregated using appropriate \texttt{perf} flags. This not only prevents data loss but also reduces the number of distinct features, thereby aligning the dataset structure more closely with the reference dataset \texttt{CICEVSE2024}. 

To establish a clear starting point for the later feature analysis, we first refer to the selected features presented in the paper \textit{Enhancing EV Charging Station Security Using A Multi-dimensional Dataset: CICEVSE2024} \cite{EV_Security}. These selected features provide a foundation for comparison and help guide our own selection process.

The \texttt{CICEVSE2024} dataset itself consists of the same 905 event types and comprises approximately 8,500 rows. Timestamps are recorded as floating-point values representing the time of each measurement. Like our dataset, it was collected using the \texttt{perf} tool, ensuring high precision and consistency across all recorded events \cite{EV_Security}. Out of the entire dataset, only four rows contain \texttt{NaN} values across all features.\\
At first glance, one might assume a high level of noise when considering the Z-Score. However, in this case, the values do not represent random noise or errors but instead correspond to peak values during attacks. Thus, the actual noise level in both datasets is very low, which can also be observed later in the direct feature comparison. Such rows with high peaks can therefore be considered meaningful signals rather than noise.\\

This is primarily due to the fact that it contains a significantly larger amount of benign data, which makes the attack data stand out more clearly as outliers. Furthermore, the benign data in the self-collected dataset is much quieter and less variable than in the \texttt{CICEVSE2024} dataset.
